# En este sitio web "https://mapas.bogota.gov.co/\#" encuentras los mapas y mucha información de la ciudad de Bogotá. Me gustaria que me ayudaras a desarrollar una aplicación (MCP) que pueda consultar los diferentes datos de un lote en particular.

Esta funcion debe alimentar a un LLM que esta haciendo evaluación de lotes para la construcción.

Sí, es totalmente viable construir un MCP para consultar un lote puntual en Mapas Bogotá y entregar un contexto estructurado a un LLM de evaluación inmobiliaria. La mejor estrategia no es automatizar el portal visual, sino consumir directamente los servicios geográficos y búsquedas publicadas por IDECA/UAECD, porque el propio sitio expone API de búsqueda, catálogo ArcGIS REST y capas de lote consultables en JSON/GeoJSON/PBF.[^1_1][^1_2][^1_3][^1_4]

## Enfoque

Mapas Bogotá publica una API con búsquedas por CHIP, geocodificación directa e inversa y acceso al catálogo de servicios geográficos del distrito.  Además, el catálogo ArcGIS REST expone la capa **Lote** dentro de `Mapa_Referencia/Mapa_Referencia`, donde el lote es una geometría poligonal y su campo visible principal es `LOTCODIGO`.[^1_2][^1_3][^1_4][^1_1]

Para una app que alimente un LLM, conviene separar el problema en dos pasos: primero identificar el lote por CHIP, dirección o coordenadas; luego enriquecerlo con capas temáticas relacionadas, como valor de referencia, destino económico predominante por lote, obras públicas cercanas, localidad, sector catastral y otras restricciones o indicadores espaciales disponibles en el catálogo.[^1_5][^1_6][^1_7][^1_8][^1_1]

## Arquitectura MCP

Te recomiendo un MCP con herramientas pequeñas y determinísticas, para que el LLM no improvise consultas GIS complejas.  Un diseño útil sería:[^1_4][^1_1]

- `resolve_lot`: acepta `chip`, `direccion` o `lat,lng` y devuelve `lotcodigo`, geometría, centroide y confianza de identificación.[^1_1][^1_4]
- `get_lot_base_context`: devuelve localidad, manzana, sector, área catastral, barrio y dirección normalizada si existen en capas relacionadas.[^1_3][^1_4][^1_1]
- `get_lot_market_context`: consulta valor de referencia y dinámica económica o destino económico por lote/manzana.[^1_7][^1_9][^1_5]
- `get_lot_risk_constraints`: consulta capas de ordenamiento, reserva vial, espacio público, obras públicas y otras restricciones relevantes para construir.[^1_10][^1_8][^1_11]
- `summarize_lot_for_llm`: consolida todo en JSON normalizado, con trazabilidad por fuente y fecha de capa.[^1_5][^1_4][^1_7]

Eso permite que el LLM reciba datos limpios como hechos observados, no HTML del portal ni texto ambiguo.[^1_4][^1_1]

## Flujo de consulta

El portal documenta una búsqueda por CHIP con `cmdBuscarCHIP` y `query=<CHIP>`, que devuelve atributos como código, nombre y geometría del predio/lote asociado.  Si el usuario no tiene CHIP, también puedes geocodificar una dirección o buscar por texto/ubicación usando latitud, longitud y distancia.[^1_2][^1_1]

Después de resolver el lote, puedes consultar la capa `Lote` del servicio `Mapa_Referencia/Mapa_Referencia` para recuperar la geometría oficial y su `LOTCODIGO`.  Con esa geometría, haces intersecciones o consultas espaciales contra capas temáticas; por ejemplo, `catastro/valorreferencia` ofrece valores de referencia del terreno y `catastro/destinolt` publica el destino económico predominante por lote.[^1_3][^1_7][^1_5][^1_4]

## Implementación sugerida

Como tú trabajas cómodo con Node.js y arquitecturas de servicios, yo lo haría como un microservicio MCP en Node con `fetch` nativo o `undici`, y con adaptadores ArcGIS REST separados por dominio. La API de Mapas Bogotá ya expone endpoints de búsqueda, y el catálogo de servicios GIS está disponible públicamente desde `serviciosgis.catastrobogota.gov.co`.[^1_1][^1_2]

Estructura recomendada:

- `providers/mapas-bogota-search.ts`: CHIP, dirección, geocoding.[^1_1]
- `providers/arcgis-query.ts`: helper genérico para `query`, `layers`, `f=pjson`, `geojson`.[^1_3][^1_4]
- `providers/lot-context.ts`: une lote + manzana + localidad + sector.[^1_4][^1_3]
- `providers/planning-context.ts`: reserva vial, obras, destino económico, etc.[^1_8][^1_11][^1_7]
- `mcp/tools/*.ts`: herramientas expuestas al LLM.
- `normalizers/*.ts`: limpia nombres de campos, fechas y nulos.
- `prompts/system-lot-evaluator.md`: instruye al LLM para no inferir normas urbanísticas no presentes en la fuente.

Un detalle importante: varias capas del ecosistema muestran año o vigencia distinta, por lo que tu JSON debe conservar `source_layer`, `service_date` y `query_timestamp` para evitar que el LLM mezcle datos 2019 con valores 2025 como si fueran una sola fotografía temporal.[^1_7][^1_5][^1_4]

```ts
import { MAPAS_BOGOTA_API } from "../config.js";
import type { ChipSearchResult } from "../types/domain.js";

export async function searchByChip(chip: string): Promise<ChipSearchResult[]> {
  const url = new URL(MAPAS_BOGOTA_API);
  url.searchParams.set("cmd", "direccion_chip");
  url.searchParams.set("query", chip);
  url.searchParams.set("spatialReference", "102100");

  const res = await fetch(url);
  if (!res.ok) throw new Error(`Mapas Bogotá API error: ${res.status}`);
  const data = await res.json();
  return data.resultados ?? [];
}
```

```ts
export async function arcgisQuery(serviceUrl: string, layerId: number | string, params: Record<string, string>) {
  const url = new URL(`${serviceUrl}/${layerId}/query`);
  Object.entries({
    f: "geojson",
    where: "1=1",
    returnGeometry: "true",
    outFields: "*",
    ...params
  }).forEach(([k, v]) => url.searchParams.set(k, v));

  const res = await fetch(url);
  if (!res.ok) throw new Error(`ArcGIS query error: ${res.status}`);
  return res.json();
}

export async function arcgisLayerInfo(serviceUrl: string, layerId: number | string) {
  const url = new URL(`${serviceUrl}/${layerId}`);
  url.searchParams.set("f", "pjson");
  const res = await fetch(url);
  if (!res.ok) throw new Error(`ArcGIS layer info error: ${res.status}`);
  return res.json();
}
```


### src/providers/lotResolver.ts

```ts
import { SERVICES, LAYERS } from "../config.js";
import { searchByChip } from "./mapasBogotaApi.js";
import { arcgisQuery } from "./arcgis.js";
import type { LotIdentity } from "../types/domain.js";

function centroidFromRings(rings?: number[][][]): { lat: number; lng: number } | undefined {
  const pts = rings?.[^2_0];
  if (!pts?.length) return undefined;
  const sum = pts.reduce((acc, [lng, lat]) => ({ lng: acc.lng + lng, lat: acc.lat + lat }), { lng: 0, lat: 0 });
  return { lng: sum.lng / pts.length, lat: sum.lat / pts.length };
}

export async function resolveLotByChip(chip: string): Promise<LotIdentity | null> {
  const chipMatches = await searchByChip(chip);
  const first = chipMatches[^2_0];
  if (!first?.GEOMETRY?.rings?.length) return null;

  const centroid = centroidFromRings(first.GEOMETRY.rings);
  if (!centroid) return null;

  const geo = `${centroid.lng},${centroid.lat}`;
  const lotGeoJson = await arcgisQuery(SERVICES.mapaReferencia, LAYERS.lote, {
    geometry: geo,
    geometryType: "esriGeometryPoint",
    inSR: "4326",
    spatialRel: "esriSpatialRelIntersects",
    outSR: "4326"
  });

  const feature = lotGeoJson.features?.[^2_0];
  const props = feature?.properties ?? {};

  return {
    chip,
    lotcodigo: props.LOTCODIGO,
    manzcodigo: props.MANZCODIGO,
    address: first.NOMBRE,
    barrio: first.BARRIO,
    geometry: feature?.geometry,
    centroid
  };
}
```

```ts
import { z } from "zod";
import { resolveLotByChip } from "../providers/lotResolver.js";
import { getDestinoEconomicoByLotcodigo, getReservaVialByPoint, getValorReferenciaByPoint } from "../providers/thematicQueries.js";

export const lotSummaryInput = z.object({
  chip: z.string().min(8)
});

export async function lotSummaryTool(input: z.infer<typeof lotSummaryInput>) {
  const lot = await resolveLotByChip(input.chip);
  if (!lot?.centroid) return { success: false, error: "Lot not found" };

  const [valor, reserva] = await Promise.all([
    getValorReferenciaByPoint(lot.centroid.lng, lot.centroid.lat),
    getReservaVialByPoint(lot.centroid.lng, lot.centroid.lat)
  ]);

  const destino = lot.lotcodigo
    ? await getDestinoEconomicoByLotcodigo(lot.lotcodigo)
    : null;

  return {
    success: true,
    input,
    lot_identity: lot,
    planning_context: {
      reserva_vial_hits: reserva?.features?.length ?? 0
    },
    market_context: {
      valor_referencia_hits: valor?.features?.length ?? 0
    },
    economic_context: {
      destino_hits: destino?.features?.length ?? 0
    },
    sources: [
      "mapas.bogota.gov.co/api",
      "Mapa_Referencia/Mapa_Referencia/MapServer/38",
      "catastro/valorreferencia/MapServer",
      "catastro/destinolt/MapServer",
      "ordenamientoterritorial/reservavial/MapServer"
    ]
  };
}
```

```python
from app.providers.arcgis import arcgis_query

def centroid_from_rings(rings):
    pts = rings[^2_0] if rings else []
    if not pts:
        return None
    lng = sum(p[^2_0] for p in pts) / len(pts)
    lat = sum(p[^2_1] for p in pts) / len(pts)
    return {"lng": lng, "lat": lat}

async def resolve_lot_by_chip(chip: str) -> LotIdentity | None:
    payload = await search_by_chip(chip)
    rows = payload.get("resultados", [])
    if not rows:
      return None

    first = rows[^2_0]
    centroid = centroid_from_rings(first.get("GEOMETRY", {}).get("rings", []))
    if not centroid:
      return None

    geo = f"{centroid['lng']},{centroid['lat']}"
    lot_geo = await arcgis_query(
        SERVICES["mapa_referencia"],
        38,
        geometry=geo,
        geometryType="esriGeometryPoint",
        inSR="4326",
        spatialRel="esriSpatialRelIntersects",
        outSR="4326"
    )

    features = lot_geo.get("features", [])
    props = features[^2_0].get("properties", {}) if features else {}

    return LotIdentity(
        chip=chip,
        lotcodigo=props.get("LOTCODIGO"),
        manzcodigo=props.get("MANZCODIGO"),
        address=first.get("NOMBRE"),
        barrio=first.get("BARRIO"),
        centroid=centroid,
        geometry=features[^2_0].get("geometry") if features else None
    )
```

Para evaluación de lotes de construcción, yo no me quedaría solo con identificación catastral y valor de referencia. # Me parece bien el siguiente paso pero ten en cuenta que para una evaluación de prefactibilidad o viabilidad es necesario evaluar las normas vigentes (POT, Decretos, UPL, etc.). Creería que eso debemos mantenerlo como embedings e implementar un RAG para cargar documentos que enriquescan el modelo de factibilidad.

Sí, ese enfoque es el correcto para una evaluación de prefactibilidad o viabilidad. Las capas GIS te dan el **contexto espacial y catastral**, pero la decisión real de factibilidad necesita además el **marco normativo vigente**: POT, decretos reglamentarios, actos complementarios y reglas por UPL o área de planeamiento; además, Bogotá tiene un POT vigente adoptado por el Decreto 555 de 2021 y existe un compendio geográfico oficial asociado publicado por la Secretaría Distrital de Planeación en Datos Abiertos.[^5_1][^5_2][^5_3][^5_4]

## Arquitectura objetivo

Yo separaría la solución en dos motores complementarios. El primero sigue siendo el MCP geoespacial para resolver lote, UPL y contexto de capas; el segundo debe ser un subsistema **RAG normativo** con embeddings sobre documentos oficiales, porque la norma no siempre está totalmente expresada como capa GIS ni como atributo simple de un servicio.[^5_3][^5_5][^5_6][^5_4]

Ese acople tiene mucho sentido porque el lote puede resolverse espacialmente contra `Lote` y `Unidad Planeamiento Local`, pero la interpretación de usos, tratamientos, cargas, condiciones y excepciones requiere consultar texto normativo y anexos vigentes. La UPL está publicada como capa poligonal oficial y puede servir como llave territorial para enrutar la búsqueda documental dentro del RAG.[^5_7][^5_5][^5_6][^5_8]

## Cómo dividirlo

La tubería debería quedar así:

- **MCP geoespacial**: resuelve lote, UPL, área de planeamiento, reserva vial, valor de referencia y demás contexto GIS.[^5_5][^5_9][^5_8][^5_10][^5_11]
- **Ingesta documental**: carga POT vigente, Decreto 555 de 2021, decretos reglamentarios, actos modificatorios, documentos técnicos y anexos relevantes desde fuentes oficiales.[^5_2][^5_4][^5_3]
- **RAG normativo**: indexa por fragmentos con metadatos como `norma`, `articulo`, `tema`, `vigencia`, `territorio`, `upl`, `tipo_suelo`, `fuente_url`.[^5_2][^5_3][^5_5]
- **Motor de factibilidad**: fusiona hechos GIS + evidencia RAG + reglas de negocio y produce una respuesta explicable, con citas a capas y a fragmentos normativos.[^5_8][^5_5][^5_2]


## Qué documentos embeder

Para la primera fase del RAG, el corpus debe priorizar documentos con fuerza normativa o interpretativa directa sobre uso y edificabilidad. El POT “Bogotá Reverdece 2022-2035” y el Decreto 555 de 2021 son el núcleo, y Datos Abiertos Bogotá publica además el compendio de información geográfica asociada al decreto.[^5_4][^5_1][^5_3][^5_2]

Yo armaría este orden de ingestión:


| Prioridad | Documento o fuente | Rol en factibilidad |
| :-- | :-- | :-- |
| Alta | Decreto 555 de 2021 [^5_2] | Norma base vigente del POT. |
| Alta | Micrositio y compendio POT en Datos Abiertos [^5_3][^5_4] | Cartografía, catálogos y recursos asociados. |
| Alta | Capas de UPL, área de planeamiento y suelo [^5_5][^5_9][^5_6] | Enrutamiento territorial para buscar reglas. |
| Media | Decretos reglamentarios y actos complementarios del POT en portales oficiales [^5_1][^5_3] | Ajustes, precisiones y desarrollo normativo. |
| Media | Documentos técnicos explicativos, anexos y catálogos de objetos [^5_4][^5_12] | Interpretación técnica y trazabilidad. |
| Baja | Material pedagógico como ABC del POT [^5_12] | Útil para explicación, no para decisión jurídica principal. |

## Diseño del RAG

La clave no es solo vectorizar PDFs completos, sino fragmentarlos con semántica jurídica y territorial. El Decreto 555 de 2021 es extenso, y el compendio geográfico del POT se distribuye con recursos complementarios y catálogos enlazados desde Datos Abiertos, por lo que conviene indexar por artículo, capítulo, anexo y tema.[^5_4][^5_2]

Metadatos mínimos por chunk:

- `document_id`
- `titulo_norma`
- `tipo_documento`
- `articulo` o `seccion`
- `vigencia`
- `jerarquia_normativa`
- `territorio_aplicable`
- `upl_codigo` cuando aplique
- `tema`: uso, edificabilidad, tratamiento, protección, cargas, movilidad, espacio público
- `fuente_url`

Con eso, el flujo de consulta sería: resolver lote -> identificar UPL y contexto territorial -> filtrar corpus por vigencia y territorio -> búsqueda vectorial + búsqueda keyword -> reranking -> respuesta con evidencia. La capa UPL oficial y el compendio geográfico del POT hacen viable ese filtrado híbrido por territorio y norma.[^5_3][^5_5][^5_4]

## Recomendación práctica

Sí mantendría normas y decretos como embeddings, pero no solo embeddings. Para algo tan sensible como prefactibilidad, usaría un esquema **hybrid RAG**: índice vectorial + metadatos estructurados + reglas determinísticas sobre vigencia y jerarquía normativa, porque un embedding puro puede recuperar un texto parecido pero no necesariamente el acto vigente o prevalente.[^5_2][^5_3][^5_4]

La siguiente versión entonces debería cambiar de objetivo: ya no solo “consultar lote”, sino “emitir contexto de factibilidad explicable”. Eso implica agregar al stack tres piezas nuevas:

- `document_ingestion`: descarga, limpia y trocea POT, decretos y anexos oficiales.[^5_4][^5_2]
- `normative_rag`: consulta por lote, UPL, tema y vigencia.[^5_5][^5_3]
- `feasibility_reasoner`: fusiona GIS + RAG + reglas del negocio para producir hipótesis de viabilidad con advertencias.[^5_8][^5_5][^5_2]
